目標架構與資料流

修改前（現況）

深淺雙 palette 色值分散寫死在 pages.py 與兩個 renderer；「市場報告／完整辯論」只在辯論室出現、離線頁回不了站內；設定混在導覽裡；設定頁顯示英文規則鍵；席名為 AI 隨手取、辯論頁看不出分工；發問選單含開放題。

修改後（預計）

design_tokens.py 成為唯一色值權威，pages.py 與兩個 renderer 一律取值；全站 header 五導覽、設定獨立；server.py 在 HTTP 回應層為離線兩頁注入導覽（檔案唯讀）；settings.py 標籤表白話化；roster 升版帶 blurb；發問選單由 market_scopes 三市場產生。

資料所有權與資料流

  • 色值：design_tokens.py → pages.py／兩個 renderer 取值；不得維護第二份色值。

Agent 分工與驗收關卡

Developer 配置

七張（01、02、03、05、06、07、09）規劃 opus-5／high：跨模組唯一權威、Schema 升版、唯讀注入契約、整包驗收等非局部小修。兩張（04、08）規劃 sonnet-5／high：固定格式文案與既有模式的局部低風險修改，可秒級驗證。升級路徑 opus-5／xhigh；max 需使用者明確核准。實際配置依執行 Task 最新使用者角色設定與後端可用性決定。

Reviewer 分工

Reviewer A 負責 Spec Review（是否符合已核准需求）；Reviewer B 負責 Standards Review（工程標準與衍生風險）。預設 both，由執行 Task 的角色設定決定；每位 Reviewer 各自載入 code-review 技能，只執行 Coordinator 指定的 review axis。

驗收關卡與 Findings 流程

  • 每張 Ticket 皆有票面測試接縫；Ready for Review 一律為 WSL 執行 python3 -m unittest discover -s tests 全綠（首次準備 Review 前執行一次，與其他票的全套測試執行權互斥）。
  • Findings 交回原 Developer 修正，或由 Developer 以證據反駁；處理後交回原 Reviewer 定向複驗，不換人裁決。
  • 每張 Ticket 的驗收結果、退出碼與必交證據將保存於該票「執行與 Review 紀錄」。
