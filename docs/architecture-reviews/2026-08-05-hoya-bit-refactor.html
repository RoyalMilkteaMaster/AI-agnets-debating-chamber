1. 決策摘要

這個專案做什麼：一套 WSL Python 控制的七席多模型（3 Codex＋3 Claude＋1 Antigravity）市場研究辯論系統——單一 launch 命令啟動七席盲投研究、T+4 證據封存、共享辯論室計票、依票數門檻產出附證據鏈的市場報告。原為黑客松比賽打造，本次健檢目標是整改為日常續用。

結論：值得整改，採「局部整理＋定向新增」（方案 A），不需要重建

理由：核心模組（debate_state_machine、report_contract、run_store）是介面小、實作厚的健康深模組，681 個測試全綠是可貴資產；使用者的五項需求全部可以在既有骨架上以「拔白名單、抽設定檔、加規則分支、清資料、加前端」達成。

最大三項風險

#風險說明
1Data Root 非 git repo，刪除不可逆整個 _data 沒有 .git。清理時若誤刪 preflight/latest-ready.json（launch 的唯一前置憑證），系統直接無法啟動，且無法從版本庫還原。
2燈號改純票數制是行為變更，不是修 bug現行燈號被四層證據品質規則（來源數/類別數/時效/可信等級）降級，且 confidence_cap 被報告驗證、Core 撰稿提示、run_verifier 三處交叉引用——改制必須三處同步，否則報告會被自己的驗證打成紅燈。
3run 目錄改日期分層動到 write-once 契約run_store 的 run-id 命名被 latest.json 指標、live_dashboard、codex_bridge、run_verifier 依賴；改 runs/日期/… 分層需同步四處＋SQLite 索引，屬中風險遷移。

4. 正式 Logging 判定

現況：沒有正式 Log。現有輸出＝①events.jsonl（append-only 稽核事件流，屬資料 artifact 不是 log）②logs/live-server.log（launcher.py:544 對 live server 子行程的 stdout 重導向，內容目前只有埠占用錯誤重複訊息）③console stderr。

判定：本次整改後「需要」最小正式 Log——因為新目標包含常駐 Web 前端（長時間無人看守的本機伺服器），符合「背景長駐程式／Web 服務」條件。建議範圍僅限新前端伺服器：啟動/關閉/請求錯誤/launch 觸發四類事件、單檔輪替、不記機密。既有研究/辯論管線已有 events.jsonl 稽核流，不需要另建 Logger。
